# NASTRAN Cross-Solver Verification — predictions frozen before execution

**Status: decks generated and predictions recorded. Not yet run.**

**Claim boundary:** educational / representative / portfolio only. Non-OEM, non-certified.

Every FE result in this project comes from one solver family. That is a single point of failure in
the verification argument: a systematic error in Ansys, or in how this project drives it, would be
invisible to every check performed so far. Agreement between two independently developed solvers on
the same problem, against the same closed-form oracle, tests something the existing benchmarks
cannot.

Following the project convention, **the predictions below were written and committed before any
NASTRAN run.** If they turn out wrong they stay in the repository.

**Decks:** `b001patch.bdf`, `b002cantilever.bdf`, `b002cantilevermodal.bdf`
**Generated by:** `src/aeroframe_dt/solver_decks.py`
**Criteria:** frozen in `BENCHMARK_LOCK.md`, 2026-07-12 — not adjustable after the fact

## 1. A generator defect found while preparing these decks

The `PBEAM` card was written with six property fields: `PID, MID, A, I1, I2, J`. The small-field
`PBEAM` order is **`PID, MID, A, I1, I2, I12, J`**. The torsional constant was therefore landing in
the **`I12` product-of-inertia field**, and `J` was left blank.

For a symmetric rectangular section `I12` must be **zero**. A non-zero `I12` rotates the principal
axes and couples the two bending planes; a blank `J` removes torsional stiffness.

**The static tip-load case would still have returned a plausible deflection.** This benchmark loads
in one plane only and does not twist, so the wrong card would very likely have passed the 0.5%
criterion and been recorded as a verification. The error would then have been carried into any
subsequent deck built on the same generator.

Fixed: `I12` now written as `0.` and `J` moved to the seventh field. This is the **third** deck-level
defect found in this project by inspection rather than by result — after `NMODIF` on attached nodes
in `patch.inp` and the `SECDATA` orientation error in `cant.inp`, both recorded in
`reports/FE_VERIFICATION_REPORT.md` §7. All three share a signature: **they produce believable
numbers.**

## 2. Oracle values

Recomputed independently for this document from the B-002 definition — `L = 1 m`, `b = 0.05 m`,
`h = 0.10 m`, `E = 70 GPa`, `ρ = 2700 kg/m³`, `P = 1000 N`:

| Quantity | Closed form | Value |
|---|---|---|
| Second moment, loaded plane | `b·h³/12` | `4.166667e-6 m⁴` |
| Tip deflection | `PL³/(3EI)` | **`1.1428571e-3 m`** |
| Tip rotation | `PL²/(2EI)` | **`1.7142857e-3 rad`** |
| Root extreme-fibre stress | `6PL/(bh²)` | **`12.000 MPa`** |
| 1st bending, strong axis | `β₁²/2π · √(EI/ρAL⁴)` | **`82.25 Hz`** |
| 2nd bending, strong axis | — | `515.47 Hz` |
| 1st bending, weak axis | `I = h·b³/12` | `41.13 Hz` |

The weak-axis frequency is listed deliberately: it is **half** the strong-axis value, so a modal run
returning `41.13 Hz` as its first mode has the section oriented wrong. That is the same trap the
`SECDATA` error sprang in the Ansys deck, where the symptom was a factor of exactly 4 in deflection.
Here the symptom is a factor of exactly 2 in frequency, because frequency goes as `√I`.

## 3. Predictions — recorded before execution

**P-1. The NASTRAN cantilever will agree with the Euler-Bernoulli oracle more closely than Ansys
BEAM188 did, and will land within 0.05% of `1.1428571e-3 m`.**

Reasoning: Ansys BEAM188 is a Timoshenko element and includes transverse shear flexibility by
default, which is why it returned **+0.57%** — over the 0.5% criterion — while its *rotation* matched
the oracle to 0.001%. Shear adds deflection but not rotation, which is exactly the signature
observed. `PBEAM` without `K1`/`K2` shear factors does not include shear flexibility, so it should
reproduce the Euler-Bernoulli oracle nearly exactly.

**If P-1 holds, it retroactively confirms the explanation given for the B-002a exceedance.** That
exceedance was attributed to shear flexibility on the basis of a hand estimate (`k = 5/6`, roughly
0.78% additional deflection — same sign and order as the 0.57% observed). An independent solver
without shear flexibility landing on the oracle would turn that from a plausible explanation into a
demonstrated one.

**P-2. The two solvers will disagree with each other by roughly 0.5%, and that disagreement will be
physics, not error.** Predicted specifically so it is not mistaken for a discrepancy later. The
correct reading of a 0.5% gap here is *two different beam theories*, not *one solver is wrong*.

**P-3. The CQUAD4 patch test will reproduce the constant-strain field to machine precision** —
displacement error below `1e-10 m`, matching the Ansys result of `4.34e-19 m`. A single undistorted
element cannot fail this. **This prediction is deliberately weak**, and stated as such: the Ansys
patch test only became meaningful once `MODMSH,DETACH` allowed the mesh to be distorted. This deck
does **not** distort the patch, so passing it demonstrates far less than B-001 did in Ansys. It is
included as a translation check, not as an element-quality test.

**P-4. The first modal frequency will be `82.25 Hz ± 1%`, not `41.13 Hz`.** If it returns near
41 Hz, the orientation vector on the `CBEAM` cards is putting the load in the wrong principal plane
and the static result should be treated as suspect regardless of how good it looked.

## 4. Acceptance

| Check | Criterion | Source |
|---|---|---|
| Cantilever tip deflection | ≤0.5% from oracle | BENCHMARK_LOCK B-002 |
| Cantilever tip rotation | ≤0.5% from oracle | B-002 |
| Patch displacement error | ≤1e-10 m | B-001 |
| Patch strain error | ≤1e-10 | B-001 |
| First bending frequency | ≤1% from `82.25 Hz` | this document |
| Cross-solver agreement | **reported, not pass/fail** | — |

The cross-solver comparison is deliberately **not** a pass/fail criterion. Two solvers agreeing does
not make either correct — they can share an error in the problem statement, which is why both are
still checked against a closed-form oracle rather than against each other.

## 6. Limitations

1. **Nothing here has been executed.** Every value in §2 is closed-form; every value in §3 is a
   prediction.
2. The patch deck is undistorted and therefore a weak test — §3, P-3.
3. Only the beam and patch benchmarks are translated. The plate benchmark (B-003) and the contact
   work have no NASTRAN counterpart, so the cross-solver check covers the simplest parts of the
   verification suite and not the parts where the project's real risk lies.
4. The `PBEAM` fix is verified by inspection of the card format only. **It has not been confirmed by
   a solver run**, which is the entire point of §5.
